# Diario peso – contesto per Claude Code

## Scopo
Web app personale, mobile-first, per registrare il peso ogni mattina e seguire un piano nutrizionale stagionale (cut finale, lean bulk, cut di fine stagione). Usata solo da telefono (iPhone, aggiunta alla schermata Home come PWA). Interfaccia in **italiano informale**, numeri con virgola decimale.

## Stack e regole
- Un solo file `index.html` con HTML, CSS e JS vanilla. **Niente framework, niente build, niente dipendenze.** Unico altro file di dati: il database dei prodotti `prodotti-it-AAAA-MM-GG.txt` (vedi Pasti).
- Nessuna chiamata di rete verso API, con una sola eccezione: la ricerca online su Open Food Facts nei Pasti quando un prodotto non e' nel database (solo il testo cercato esce dal telefono). Altra risorsa esterna: Google Fonts (Barlow, Barlow Condensed) con fallback di sistema.
- Dati salvati in `localStorage` (solo sul dispositivo):
  - `diario_peso` -> oggetto `{ "YYYY-MM-DD": { date, kg } }`
  - `diario_vita`  -> oggetto `{ "YYYY-MM-DD": { date, cm } }`
  - `diario_kcal`  -> oggetto `{ "YYYY-MM-DD": { date, adh: "si"|"circa"|"no", kcal? } }` (giorno a cui si riferisce il mangiare). Dalla v1.10 l'utente scrive solo le kcal: `adh` viene calcolato (`adhOf`) e salvato insieme, cosi' il formato non cambia; quando `kcal` c'e' vince sempre su `adh`. Le voci vecchie senza kcal tengono il loro `adh`. Dalla v1.17 il totale dei Pasti scrive qui la voce del giorno con `src:"pasti"` (sovrascrive una voce scritta a mano solo se aggiungi pasti a quel giorno; se togli tutti i pasti si cancellano solo le voci `src:"pasti"`).
  - `diario_report` -> oggetto `{ "YYYY-MM-DD"(lunedi'): { mon, sun, n, avg, rate, dv, dw, adh:{n,si,circa,no,kAvg}, ph, st, dir, two, streak, badges:[...], stars, notes, vc, vt, vx, seen, made } }` (report settimanali congelati: l'ultimo si ricalcola finche' non premi "Ok, visto", poi resta fisso)
  - `diario_adj`   -> array `[ { date, ph, dk, mon } ]` (correzioni kcal accettate: valgono da `date` in poi, solo nella fase `ph`; `dk` = +/-150, tutto sui carboidrati)
  - `diario_meta`  -> oggetto `{ lastBackup: "YYYY-MM-DD", chartWaist: bool, weekSeen: "YYYY-MM-DD", meals: { pasto: { pct } }, recent: [id] }` (impostazioni e promemoria, non dati di misura; `meals` = percentuali dei pasti, `recent` = cronologia della ricerca)
  - `diario_cibi`  -> oggetto `{ id: { id, n, b, k, p, c, g, u:{n,g}|null, u2:{n,g}|null, src:"mio"|"off" } }` (cibi tuoi e prodotti scelti, valori per 100 g; `u` porzione/unita', `u2` confezione; id `m:...` creati da te, `o:codice` Open Food Facts)
  - `diario_pasti` -> oggetto `{ "YYYY-MM-DD": { colazione|pranzo|merenda|cena: { items:[ { f, n, b, q, u, un, per:{k,p,c,g}|null, k, p, c, g } ], skip? } } }` (voci gia' calcolate; `per:null` e `b:"stima"` = Pasto veloce)
- **Non cambiare mai il formato di queste chiavi senza scrivere una migrazione**: l'utente ha dati reali. Backup/ripristino in JSON: `{ v: 4, exported, weights, waists, kcal, reports, adj, foods, meals }`; il ripristino accetta anche i backup `v: 1`/`v: 2`/`v: 3` (senza `kcal`/`reports`/`foods`/`meals`) e controlla ogni report con `validReport`, ogni cibo con `validFood`, ogni giorno di pasti con `cleanDay`.
- PWA: `manifest.webmanifest`, `sw.js` (network-first, fallback cache; il database dei prodotti invece prima dalla cache, in una cache sua `diario-peso-prodotti` che non si svuota a ogni versione), icone `icon-192.png`, `icon-512.png`, `apple-touch-icon.png`. Tutti i percorsi sono **relativi** (`./`) perche' il sito sta in una sottocartella di GitHub Pages.
- Su iOS la PWA aggiunta alla Home ha uno storage separato da Safari: i dati inseriti in Safari non compaiono nell'icona. Usare solo l'icona, oppure passare i dati col backup.

## Struttura di index.html
Quattro tab: **Diario** (in cima `#todo`: card della pesata spostata li' se manca quella di oggi + card "Pasti di ieri" (`#kcalCard`: riassunto kcal/macro di ieri, pallini della settimana, tasto che apre Pasti; le kcal scritte a mano prima della v1.17 si vedono come "Totale scritto a mano") se manca ieri + report della settimana precedente (lun-dom, con stelle, premi e malus, da lunedi' finche' non premi "Ok, visto") + avviso backup oltre 30 giorni; poi peso, grafico con vita attivabile, verdetto, vita nascosta in un `<details>`, ultime pesate, incolla pesate, backup; la card del peso mostra "🍽️ oggi X / obiettivo kcal"), **Pasti** (vedi sotto), **Piano** (timeline colorata delle fasi, dettaglio kcal/macro con le correzioni, mantenimento reale stimato, elenco delle correzioni da annullare), **Goals** (barre di avanzamento, vita, costanza, kcal rispettate, report settimanali salvati da riaprire con un tocco, traguardi).
Nel JS: `PLAN` (punti di traiettoria peso), `PH` (fasi con kcal e macro), `GOALS`, `PLANLAB`, funzioni `verdict`, `render*`, `save/remove` (+`saveW/removeW` per la vita).

## Il piano (fonte di verita' in `PH` e `PLAN`)
| Fase | Periodo | Kcal | P / C / G (g) |
|---|---|---|---|
| Cut finale | 5 ott – 16 ott 2026 | 1900 | 162 / 212 / 42 |
| Ricarica pre-partita (giorno prima e giorno della prima partita, dom 18 ott; non un carb load vero, solo arrivare carico dopo il cut) | 17 – 18 ott | 2400 | 160 / 340 / 45 |
| Transizione | 19 – 25 ott | 2300 | 160 / 290 / 55 |
| Lean bulk | 26 ott – 4 apr 2027 | 2500 | 160 / 340 / 55 |
| Cut soft | 5 – 25 apr | 2250 | 170 / 270 / 55 |
| Cut pieno | 26 apr – 14 giu | 2100 | 170 / 245 / 50 |
| Uscita | 15 – 28 giu | 2300 poi 2500 | 160 / 290 / 55 |

Traiettoria peso attesa (`PLAN`): 6 ott 77,4 (partenza reale) – 16 ott 76,7 (fine cut) – 5 nov 78,1 – 5 dic 78,8 – 5 gen 79,5 – 5 feb 80,2 – 5 mar 80,8 – 5 apr 81,4 – 25 apr 80,5 – 14 giu 77,4 (kg, media settimanale). Il piano iniziale partiva da 78,5: tutti i punti sono stati spostati di -1,1 kg mantenendo gli stessi ritmi. `GOALS` usa gli stessi valori (cut 77,4 -> 76,7; bulk 76,7 -> 81,4; cut di fine stagione 81,4 -> 77,4).

Regole del verdetto (calcolate su media 7 giorni vs 7 giorni prima, servono almeno 3 pesate per finestra):
- Bulk: ritmo <0,1 kg/sett -> +150 kcal; >0,4 -> -150; vita +1,5 cm in 10+ giorni con peso in salita -> -150; altrimenti ok (obiettivo +0,15/+0,25).
- Ricarica pre-partita: sempre ok (il peso sale per acqua e glicogeno, non si cambia niente).
- Transizione: scende piu' di 0,3 kg/sett -> +150; altrimenti ok.
- Cut: scende piu' di 0,7 kg/sett -> +150; peso fermo (> -0,1) -> -100/150; altrimenti ok.
- Allarme sul trend (`BAND`, `trend()`): fascia giusta in kg/sett = cut/cut soft/cut pieno [-0,7; -0,1], bulk [+0,1; +0,4], transizione [-0,3; nessun limite]; ricarica e uscita senza fascia. In fascia = 🟢 in linea; fuori = 🟡 attenzione; fuori di oltre 0,25 kg/sett o fuori dallo stesso lato anche la settimana prima = 🔴 fuori rotta. Sopra la fascia = "mangi troppo", sotto = "mangi troppo poco" (nel bulk conta anche la vita +1,5 cm). Lo stato colora verdetto, anello della card del peso, chip in alto e riepilogo settimanale; i colori delle fasi restano.
- Report settimanale (`buildReport`): premi 🏅 7/7 pesate, 🎯 kcal rispettate >= 90% (almeno 5 giorni), 📈 ritmo in fascia, 🧭 media entro 0,3 kg dal piano, 🔥 3+ settimane di fila in linea; malus 😴 <= 3 pesate, 🍕 kcal rispettate < 60% (almeno 4 giorni) per lo piu' sopra / 🍽️ per lo piu' sotto, 🚀 fuori rotta per eccesso, 🪫 fuori rotta per difetto, 📏 vita +1 cm. Stelle = 3 + premi - malus, tra 1 e 5.
- Correzione di kcal e macro (`proposal`, `target`): solo nel report del lunedi', solo se il "Perche'?" della settimana dice 🧮 piano, solo in cut, cut soft, cut pieno e bulk, e solo se la settimana chiusa e' 🔴 fuori rotta e nella stessa fase della settimana che inizia. Propone +150 (mangi troppo poco) o -150 (mangi troppo) kcal, tutte sui carboidrati (+/-38 g); proteine e grassi fissi. Niente proposta se: correzione nella stessa fase da meno di 14 giorni (aspetta), meno di 4 giorni con le kcal (mancano i dati), causa = quanto mangi (prima rispetta le kcal), o totale della fase oltre +/-300 (parlane col nutrizionista). La proposta si applica solo col tasto Applica (l'utente conferma); "Ok, visto" senza scegliere = lasciata stare. Le correzioni si annullano nel Piano. Tutto l'app usa `target(d)` = fase + correzioni.
- Soglie per anticipare il cut: vita >= 87 cm, peso medio >= 83 kg.
- Aderenza dalle kcal scritte: entro +/-100 dall'obiettivo del giorno (`target`) = rispettate, entro +/-250 = vicino, oltre = fuori sopra/sotto. Punteggio rispettate=1, vicino=0,5, fuori=0.
- "Perche'?" (`cause`, `whyText`), quando lo stato e' 🟡 o 🔴: con almeno 5 giorni di kcal negli ultimi 14 (4 nella settimana per il report) guarda la media delle kcal rispetto all'obiettivo. Se e' oltre 100 kcal dalla stessa parte del trend (sali troppo e mangi sopra, scendi troppo e mangi sotto) = 🍕 sono gli sgarri / 🍽️ mangi meno, non il piano: niente correzione. Altrimenti = 🧮 e' il piano (le kcal le rispetti, o mangi gia' dalla parte opposta). Senza kcal ma con voci vecchie si'/circa/no usa il punteggio (< 70% = colpa tua). Senza dati = ❓.
- Mantenimento reale: ultime 4 settimane, media kcal registrate - pendenza del peso (retta dei minimi quadrati, kg/giorno) x 7700; servono 14 giorni con kcal e 10 pesate su almeno 14 giorni.
Se si cambia il piano, aggiornare **sia** `PH`/`PLAN`/`GOALS` **sia** questa tabella.

## Design
Palette vivace con token CSS su `:root` (chiaro) e override scuro in `@media (prefers-color-scheme: dark)` e `[data-theme="dark"]`. Ogni fase ha un colore (`--c-cut`, `--c-carb`, `--c-trans`, `--c-bulk`, `--c-cutsoft`, `--c-cutfull`, `--c-out`) e il testo relativo (`--on-*`): la card del peso prende il colore della fase corrente. Tab colorate (Diario viola, Pasti col colore `--c-out`, Piano verde, Goals arancione). Font: Barlow Condensed per i numeri grandi, Barlow per il testo. Rispettare `env(safe-area-inset-*)` e `viewport-fit=cover`. Mantenere contrasto leggibile e target touch >= 44 px.

## Beta: provare prima di pubblicare
- `beta/` contiene la versione di prova: lo **stesso** `index.html` dell'app con le novita', piu' copie di `sw.js` (CACHE `diario-peso-beta-...`), `manifest.webmanifest` e icone. Indirizzo: `https://danielebenyacar.github.io/DASHBOARD-PESO-DIETA/beta/`, da aprire in **Safari** (storage separato dall'icona).
- In `/beta/` il codice usa da solo il prefisso `beta_` per tutte le chiavi `localStorage` (`BETA`, `PFX`, `lsGet`/`lsPut`), mostra la fascia "Versione BETA" e aggiunge "· BETA" al footer: la beta non tocca mai i dati dell'app vera. Per provarla coi dati veri: backup dall'icona e "Ripristina da backup" nella beta.
- Ogni novita' va prima in beta; quando l'utente approva: copia `beta/index.html` in `index.html` (fuori da `/beta/` il prefisso e' vuoto) e, se cambia, il database `prodotti-it-*.txt`; aumenta CACHE in `sw.js` e `beta/sw.js` e il footer, aggiorna questo file. Non copiare `beta/sw.js` sopra `sw.js`: le cache hanno nomi diversi (`diario-peso-...` / `diario-peso-beta-...`) e ognuno cancella solo le sue. I dati della beta (in Safari, prefisso `beta_`) non passano all'app vera.
- Adesso la beta e' uguale all'app vera (v1.17).

## Pasti (diario alimentare)
- **Tab Pasti** (dalla v1.17 nell'app vera; quarto tab, stile Nutrium coi colori dell'app, senza orari dei pasti). Diario alimentare: riga con lo stato del peso e il "Perche'?" (tocco = verdetto nel Diario), settimana con giorni ✓/↑/↓, serie 🔥, semicerchio consumato/obiettivo, barre P/C/G, card colazione/pranzo/merenda/cena con stato completato/lontano/saltato. Scheda del pasto: obiettivo, illustrazione, macro, cibi (✎ modifica, × togli), salta pasto. **Ricerca di alimenti** come Nutrium: ✕, + in alto = crea alimento, campo con 🔍, "✏️ Pasto veloce" (descrizione a tutta riga + kcal e P/C/G facoltativi, per pasti fuori o cibi senza etichetta; voce del pasto con `b:"stima"`, `per:null`; si ritrova per nome nella ricerca e nella cronologia: `estFoods()` lo legge dai pasti salvati, a parita' di nome vale l'ultimo, id `s:nome`, mostrato come "1 piatto"; il tocco riapre la scheda gia' compilata, il + lo rimette uguale; nessuna chiave nuova), Cronologia (recenti) e risultati con nome, ✓ per i cibi base, "kcal, porzione, fonte" e **+** che aggiunge subito la porzione predefinita (avviso in basso). **Aggiungere alimento**: quantita' + menu unita' (Grammi / 1 porzione / 1 confezione / unita' del cibo), kcal e P/C/G con % per 100 g, "Fonte", correzione valori per i prodotti online, Salvare in alto e in basso; plurali delle unita' (2 porzioni). Piano alimentare: percentuali dei pasti (default 20/35/15, la cena prende quello che resta). Il totale del giorno va in `diario_kcal` con `src:"pasti"`. Nel Diario la card "Pasti di ieri" (al posto del campo kcal a mano) riassume ieri e porta a Pasti; la card del peso mostra "🍽️ oggi X / obiettivo kcal".
- Chiavi (vedi sopra): `diario_cibi` (`{ id: { id, n, b, k, p, c, g, u:{n,g}|null, u2:{n,g}|null, src:"mio"|"off" } }`, per 100 g; `u` porzione/unita', `u2` confezione), `diario_pasti` (`{ giorno: { pasto: { items:[ { f, n, b, q, u, un, per:{k,p,c,g}|null, k, p, c, g } ], skip? } } }`), in `diario_meta` anche `meals` (percentuali) e `recent`. Backup `v: 4` con `foods` e `meals` (ripristino con `validFood`/`cleanDay`).
- **Database dei prodotti**: `prodotti-it-AAAA-MM-GG.txt` (stessa copia in `beta/`), prodotti venduti in Italia da Open Food Facts (licenza **ODbL 1.0**: citare la fonte, il file resta sotto ODbL; la nota e' nella ricerca vuota). Formato: prima riga `#prodotti-it<TAB>data<TAB>licenza<TAB>n`, poi `codice, nome, marca, kcal, P, C, G (per 100 g), porzione g, confezione g` separati da TAB, gia' in ordine di popolarita' in Italia. Si crea con `tools/prodotti.py` (solo libreria standard; istruzioni in testa al file): tiene solo prodotti con kcal e P/C/G coerenti, scansionati in Italia o con codice a barre italiano, un solo prodotto per nome+marca. Per aggiornarlo: nuovo file con la data nella radice e in `beta/`, `DB_URL` in index.html, versioni in sw.js, beta/sw.js e footer, togliere i file vecchi. Si scarica quando apri la ricerca; `sw.js` lo tiene in una cache sua (`diario-peso-prodotti`, in beta `diario-peso-beta-prodotti`; prima la cache) che non si svuota a ogni versione. Ricerca (`dbSearch`, chiavi `sKey`): ogni parola deve essere l'inizio di una parola di nome o marca, senza accenti e con le doppie ridotte a una ("chico" trova Chicco, "mozarela" la mozzarella; vale anche per i tuoi cibi); se nessuno ha tutte le parole mostra "Prodotti simili" con tutte tranne una; prima chi comincia con la parola cercata, poi parole intere, poi i piu' popolari; massimo 40. Nei risultati il **+** diventa una spunta verde ✓ se quel cibo e' gia' nel pasto (`mealIds`; toccandola ne aggiungi ancora). I prodotti scelti finiscono in `diario_cibi` come `o:codice`, `src:"off"`.
- Quantita' proposta col + (`defUnit`): porzione/unita' del cibo; la confezione solo se e' fino a 400 g e 600 kcal, se no 100 g.
- Eccezione alla regola "niente rete": se un prodotto non e' nel database, "Non lo trovi? Cerca anche online" su `it.openfoodfacts.org/cgi/search.pl` (Open Food Facts risponde spesso 503 "occupato", senza CORS: si riprova da solo fino a 3 volte, attesa 20 s per tentativo, poi "↻ Riprova"; `search.openfoodfacts.org` non accetta richieste da altri siti, CORS). Solo il testo cercato esce dal telefono. Invio/🔍 cerca online solo se il database non si e' caricato. Niente codici a barre (scelta dell'utente).

## Come lavorare
1. Modifica solo cio' che serve, mantenendo il file unico e l'impostazione delle quattro tab.
2. Prova in locale: `python3 -m http.server 8000` e apri `http://localhost:8000` (il service worker richiede http/https, non `file://`). Controlla la console senza errori e prova viewport 390x844, tema chiaro e scuro.
3. **Ad ogni modifica a index.html o agli asset**: incrementa la versione in `sw.js` (`CACHE`) e nel footer `v1.x` di `index.html`, cosi' il telefono scarica l'aggiornamento. Le novita' vanno prima in `beta/` (vedi sopra).
4. Commit chiari in italiano, poi `git push` su `main`. GitHub Pages pubblica da `main` / root (anche `beta/`).
5. Mai committare dati personali dell'utente (esportazioni CSV/JSON). Il repo e' pubblico: nessun segreto e nessun dato di peso reale.
